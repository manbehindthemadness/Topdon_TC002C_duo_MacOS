TC002C Duo hardware and TISR investigation
========================================
Research date: 2026-10-04
Scope: this connected camera and firmware, Linux USB capture, and static
inspection of TOPDON's official Android APK. No iOS app inspection or trace.

Results and application opportunities
------------------------------------
* Ambient temperature, distance and emissivity are hardware corrections.
  Reflected temperature and optical transmission also change the radiometric
  output. Humidity is writable; a useful effect was not established at 1 m.
* Hardware preview processing includes brightness, contrast, denoising, detail
  enhancement, 15 palette selections, and mirrors. Measurements must remain
  separate from display enhancement.
* Six stream formats were captured. Temperature-only capture reduces each frame
  from 496,160 to 98,440 bytes; preview-only capture is 393,216 bytes.
* TOPDON advertises TISR: native 256x192 enhanced to 512x384. The official
  Android TC002C Duo activity's TISR switch activates HOST display processing.
  Its normal 2x path reaches Anime4KCPP's Anime4K09 through libASupCPPCore.so. The
  generic camera SDK's AI-super-resolution field is a different interface and
  its write was ignored here. This does not negate the advertised TISR feature.
* The phone polls hardware initialization status before streaming. This gives
  us a concrete startup-readiness condition, rather than a guessed delay.
* The toolbar ambient adjustment remains a software background anchor. The
  subsequently implemented Camera popup supplies the verified hardware rows;
  editing a hardware correction selects raw/64 - 50 conversion, and restoring
  camera settings returns to the software anchor. Readings remain approximate.
  See README.md for current application behavior; these notes document research.

Evidence, preservation and limits
--------------------------------
63 configuration trials were run, including repeated status-validation trials,
plus two manual-shutter transfer probes. Every reversible configuration trial
used saved complete payloads and restoration. Readback failure counts as an
unsupported/ignored trial, not a successful setting change.

The preserved experimental starting state was 30 C ambient, 1.00 m distance,
0.80 emissivity. Earlier phone defaults were 22 C, 0.25 m, 0.95; do not substitute
those defaults for the actual starting state. Hardware capability data reports
a 30 cm minimum distance. All six saved configuration blocks were compared
byte-for-byte after testing. Stream reopening also restores initial active
pixel ordering after corridor tests.

Verified USB control sequence
-----------------------------
All requests below use wIndex=0x0A00. A configuration command is selected with:
  SET_CUR: bmRequestType=0x21, bRequest=1, wValue=0x0500,
           payload=[data_selector, command]
  GET_LEN: bmRequestType=0xA1, bRequest=0x85,
           wValue=data_selector << 8, requested length=4
           This camera returns TWO bytes; accept 2 or 4, bound the decoded size.
  GET_CUR: bmRequestType=0xA1, bRequest=0x81,
           wValue=data_selector << 8, returned configuration length

To update a known configuration:
  read and preserve the complete original payload;
  select -> GET_LEN -> SET_CUR(full modified payload);
  poll fresh selections and GET_CUR until the complete payload matches;
  verify changed frame data; restore the original complete payload afterward.
Do not insert GET_CUR between command selection and the actual SET_CUR write.
Readbacks can lag. USB transfer completion alone does not prove application.
Unsupported getters may return stale data from a previous selection, so a
plausible response is insufficient to validate a new command.

Protocol version uses selector 4 directly: GET_LEN then GET_CUR -> "2.0\0".
Command state uses selector 6 directly: GET_LEN then GET_CUR, one-byte status.
0=success, 1=not ready, 2=wrong state, 4=out of range, 8=invalid value,
9=unsupported subfunction. Other SDK codes are in USB_COMMAND_STATE.
IMPORTANT: our ignored AI-super-resolution write still returned state 0.
Use both status AND readback/frame validation.

Configuration blocks and wire offsets
-------------------------------------
Offsets are relative to configuration bytes, not SDK host C structures.
All integers below are little-endian. Preserve every unlisted field.
Do not infer wire layouts from a different SDK version's struct size.

selector 2 / command 1: brightness, 2 bytes, value at byte 1 (0..100).
selector 2 / command 2: contrast,   2 bytes, value at byte 1 (0..100).
selector 2 / command 5: enhancement, 79 bytes:
  0 channel
  1 noise mode: 0 off, 1 general, 2 expert (capability mask=7)
  2 general noise level; 3 spatial; 4 temporal (0..100)
  5 palette: tested original 1 and alternatives 2,10..22
  6 detail enable; 7 detail level (0..100)
  20 edge enable, 21 edge level: enabling was ignored
  22 wide-temperature-work: tested value 2 ignored
  23 ISP AGC mode: tested value 0 ignored
  24 AI super resolution: enabling ignored, capability flag=0
  68 raw radiometric denoise: disabling ignored
  78 auto-shutter enable: not tested; phone uses a separate serial command
  Burn protection and other unlisted fields were preserved, not modified.

selector 2 / command 6: video adjustment, 31 bytes:
  0 channel; 1 mirror; 2 frequency; 3 corridor rotation
  mirror 0 original, 1 both axes, 2 horizontal, 3 vertical.
  Both raw temperatures and preview follow these mirrors.
  Zoom and cursor capabilities are absent. Bad-pixel capability exists but
  bad-pixel/calibration fields were not written.

selector 3 / command 1: thermometry, 80 bytes:
  5 temperature unit: 1 C, 2 F, 3 K
  6 range: original 2, candidate high range 3
  16 uint32 emissivity percent (0.80 -> 80)
  21 uint32 distance centimeters (1.00 m -> 100)
  25 reflected-temperature enable; 26 uint32 (C+100)*10
  31 stream overlay flag
  40 uint32 optical transmission percent
  44 center display flag
  69 uint32 relative humidity, percent*10
  75 ambient enable: 1 disabled, 2 enabled
  76 uint32 ambient temperature, (C+100)*100 (30 C -> 13000)

Distance capability reports 30..9900 cm; emissivity 1..100 percent.
Capability limits require independent validation before UI range exposure.

selector 3 / command 5: stream configuration, 14 bytes.
All saved bytes restored after mode changes. Width/height and 50 fps writes
were ignored in this negotiated 25 fps capture path.

Observed correction effects
---------------------------
Compared with nearby baseline captures using raw/64 - 50:
  emissivity 0.95: approximately +2.02 C median; 0.50: -8.19 C
  distance 0.30 m: approximately +0.73 C; 5.00 m: -1.91 C
  ambient 20 C: approximately +2.94 C; 40 C: -3.60 C
  reflected 15 C enabled: approximately +3.76 C; 35 C: -1.66 C
  optical transmission 95%: approximately +0.38 C
These are this scene's changes, with possible scene drift, not correction
formulas or accuracy measurements. Humidity changes had little/no observable
median effect at 1 m. Fahrenheit selection did not convert the stream's raw
plane or telemetry out of Celsius. Display units belong in host presentation.

Range capability entries advertise ID 2 (-20..150 C) and ID 3 (0..550 C).
ID 1 was ignored. ID 3 read back successfully, but initial post-reopen frames
were frozen and header telemetry inconsistent. ID 9 was ignored. ID 3 must not
be exposed as a validated operational high range yet. Restoring ID 2 returned
live data. Overlay-off was ignored; center-display-on was accepted without an
established text overlay effect.

Preview processing and orientation
----------------------------------
Brightness 30/70 visibly shifted preview intensities. Contrast, noise controls
and detail settings accepted full-payload roundtrips. Turning noise processing
off increased measured preview temporal variation; this was not a controlled
SNR benchmark. Temperature-plane correlation stayed >0.998 in image-only tests.
Color palettes add real U/V chroma to the YUYV preview. Our existing luma-only
preview decoder discards that color, so hardware palette integration needs
proper YUYV conversion rather than applying a second palette to luma.

Corridor quirk: saved original corridor=1, but a newly opened stream has normal
pixel ordering. Writing the original block activates 90-degree rotation with
unchanged header dimensions. A normal reshape then makes stripes. Correct
portrait reshape plus inverse transpose/flip recovered >0.998 correlation.
Reopening restores normal active ordering while preserving the saved bytes.
Prefer current software orientation until this state distinction is handled.
Isolated mirror tests used corridor=0 and recovered raw/preview correlations
around 0.998/0.999 after inverse mirroring.

Captured stream modes
---------------------
mode   bytes/frame   established layout
 2        98,440     136-byte header + 256x192 uint16 temperature plane
 3       100,352     98,304-byte sensor-count plane + 2,048 trailing bytes;
                    temperature conversion NOT established
 6       395,880     2,668-byte header + 512x384 YUYV preview
 8       496,160     4,640-byte header + 98,304 temperatures + 393,216 YUYV

                    counts differ from calibrated mode-8 temperatures
10       393,216     pure 512x384 YUYV preview, no header

These six modes agree with stream capability mask 0x3A6. Production's current
assembler assumes mode 8 magic and frame length and must be adapted for others.
Native thermometry remains 256x192; preview dimensions do not imply independent
512x384 temperature measurements.

Mode-8 header offsets (from beginning of assembled frame):
  0 magic 0x70827773
  4 header length excluding magic (4636)
  128 four float32 correction values: distance cm, a currently unknown value
      observed as 1200, emissivity percent, ambient C
  144 three float32 scene summaries: min C, max C, average C
  4636 marker 0xAABBCCDD
  4640 radiometric uint16 data
  102944 preview YUYV data
Earlier float quadruple interpretations must not label the unknown second
float as a verified humidity value.

Native conversion raw/64 - 50 matched header min/max/average with typical
median differences of roughly 0.02..0.2 C. Some captures had larger deviations
and an outlier >5 C; timing, scene changes and invalid pixels need handling.
There was no calibrated temperature reference. The phone callback adds 14272
to counts before downstream temperature handling; that is consistent with
conversion to Kelvin*64 (14272/64=223), not new thermal information.

TISR: official Android implementation
------------------------------------
Official APK obtained through TOPDON's public TC002C Duo download endpoint:
  TopInfraredV6.00.005_0812_1604.apk
  SHA256 c7c6ad29e7fc75cf60187c067312bb4192ba9301991fb834f8ac557bfb32f8a0
No APK execution occurred. Focused DEX decompilation and native symbol inspection
were used. Some large methods fail decompilation; treat incomplete methods as
unknown rather than reliable code.

Directly established call path for normal TC002C Duo TISR:
  com.topdon.hik.activity.TC02CDuoThermalActivity.switchAmplify
    -> initialize SupHelp.initA4KCPP; toggle AmplifyLevel.OFF/MIDDLE
    -> HikSurfaceView.setOpenAmplify
    -> HikSurfaceView.refresh: palette conversion, rotation/mirror,
       OpencvTools.supImage on display pixels
    -> com.example.suplib.wrapper.SupHelp.runImage
    -> An4K.loadImageMat / process / saveImageToMat
    -> An4KCreator.create(parameters, GPU), selecting An4KGPU
    -> An4KGPU.createAn4KGPUByArgs in libASupCPPCore.so
    -> Anime4KCPP::OpenCL::Anime4K09 constructor

The display scale is 2 when this path is active. ARM64 disassembly establishes
the native constructor: call at 0x34b5fc selects OpenCL::Anime4K09, a rule-based
algorithm. The separate An4KGPUCNN constructor selects ACNet. Public ACNet
HDN0-3 weights match the bundled CPU arrays within float rounding precision;
their presence does not mean the normal TISR path uses them. See
anime-enhancement.txt for source versions, parameters and runnable model tests.
The APK also contains
NCNN up2x models and an MNN ai.mnn model. The Duo activity restricts its separate
MNN/ESRGAN high-mode popup to deviceType==96. Presence of those assets does not
prove they are the ordinary TC002C Duo TISR implementation.

The inspected phone callback expects a 256x192 YUYV preview, whereas our
negotiated stream contains a 512x384 preview. Do not blindly add another 2x
scale to our 512x384 data and call it the advertised 512x384 TISR. Reproduce the
appropriate input size, processing and output size and compare the same scene.
This is Android evidence, not proof of the iOS app's internal algorithm.

Useful next integration: build an optional host enhancement using a compatible
open-source Anime4K09 implementation, compare ACNet separately against our existing
filters on preserved captures, and leave saved raw measurements untouched.
Do not redistribute extracted vendor binaries/models as part of the application.

Startup and shutter leads
-------------------------
selector 1 / command 4 returns three-byte hardware status, observed 01 02 02.
The official phone waits for byDeviceInitialStatus==2, polling every 200 ms,
before it starts capture. Add bounded readiness polling and useful diagnostics
when implementing this path; fresh replug behavior still needs validation.
Java release calls stop channel, logout and cleanup. No explicit custom
shutdown command was established; native cleanup remains untraced.

Manual shutter: selector 2 / command 4 accepts a one-byte transfer. Both 0 and
1 probes completed; the latter returned command status 0. Configuration bytes
remained unchanged. A conclusive mechanical/NUC event was not established.
Do not conflate this with cover calibration.

Phone auto-shutter uses USB_SetSystemSerialData:
  selector 1 / command 24, 11-byte payload, little-endian:
  byte 0 mode (1 read, 2 write), uint16 flag at 1,
  uint32 device command at 3, uint32 value at 7.
  Phone write: mode=2, flag=0, command=0x2001, value=0/1.
A read-mode probe (mode=1, flag=0, command=0x2001) returned eleven zero bytes,
which did not echo the requested command or establish the original value.
Therefore no auto-shutter configuration writes were performed. The startup
clicking behavior cannot yet be attributed to this control.

Phone cover calibration command 0xF026/value 2 and SDK expert correction exist
but were not invoked. Other capability-only leads include calibration-file
access, diagnostic logs and dead-pixel handling. Region/fusion getters sometimes
returned stale data; support was not demonstrated and must not be advertised.

Suggested implementation order
------------------------------
1. Hardware readiness + full-payload preservation/readback control transport.
2. Hardware emissivity/distance/ambient controls, separately named from the
   existing software ambient anchor. Verify native temperature conversion
   before removing that anchor or combining corrections.
3. Host TISR-compatible display enhancement, with fixed native measurement
   coordinates and raw saves. Compare the scene from the phone screenshots.
4. Hardware brightness/contrast/noise/detail and YUYV color conversion.
5. Lower-bandwidth stream formats when required; retain mode 8 for telemetry.
6. Longer-settling range trials and auto-shutter readback/persistence work.

Shutter / frozen-frame investigation (2026-10-05)
------------------------------------------------
Read-only, 120-second mode-8 capture: 2,998 frames at approximately 25 Hz.
The viewer was closed to release USB ownership. No hardware controls were
written. Local evidence: diagnostics/shutter-audit/{frames.csv,headers.npy,
raw.npy,frame-count.txt,event-montage.png,replay.py}. Arrays have unused
preallocated rows; use only the frame count recorded in frame-count.txt.

A little-endian uint32 at byte 32 changed from 0 to 1 for frames 1164..1179
(elapsed 46.6197..47.2193 seconds). These 16 frames repeated the temperature
plane from frame 1163 exactly. Live temperature pixels resumed at frame 1180.
At 25 Hz this is about 0.64 seconds of frozen radiometry. Frame sequence
numbers continued advancing. The user heard a click during this capture;
the sound itself was not timestamped or recorded.

Device-research corroboration:
- Related HCUSBSDK header USB_STREAM_FS_SUPPLE_INFO_TEMP contains four DWORDs:
  dwTmDataMode, dwTmScale, dwTmOffset, dwIsFreezedata. The freeze field is
  documented as 1 frozen / 0 not frozen. Local source:
  diagnostics/telemetry-research/module-search/HCUsbSDK.h, lines 2578..2584.
- Our mode-8 DWORDs at bytes 20,24,28,32 are [1,1,0,freeze], consistent with
  a two-byte temperature format and this supplementary block. This mapping
  is an inference supported by the actual freeze/repeat event, not an exact
  TOPDON header definition. The older SDK's complete stream structures order
  blocks differently; do not apply their whole struct directly to our stream.
  In particular, its scale/offset fields do not establish TOPDON's Celsius
  conversion. raw/64-50 remains independently verified for this camera.
- Native SDK strings also expose byIsFreezedata in appended radiometric JPEG
  data. That corroborates generic frozen-data semantics; it does not establish
  the cause of every frozen frame or the offset in our mode-8 stream.
- Phone CalibrationTools.shutter dispatches tc1bShutterManual for one device
  family, otherwise updateOOCOrB(B_UPDATE); autoShutter uses a separate
  shutter-property command. These are multiple device families, so they are
  leads rather than proof that every command applies to the TC002C Duo.

TOPDON's manual describes clicking as normal automatic shutter operation
used to refresh image clarity. The observed flag is best treated as 'data
frozen', with shutter calibration the observed likely cause. No 0 or 65535
raw pixels occurred in this capture, and the flagged frames were repetitions,
not corrupt temperatures. Thus this event alone does not establish the cause
of every previously reported temperature spike. A synthetic single-65535
pixel experiment separately demonstrated that unchecked averaging can keep
an impossible maximum visible across subsequent good frames.

Implemented handling: frozen frames and frames containing raw endpoint
counts 0/65535 hold the last valid image/readings, expose a status, skip
calibration sampling and CSV samples, and create gaps in graph histories.
Temporal averaging restarts from the first valid frame after a pause. Startup
without a valid frame shows unavailable temperatures. Capture metadata
records measurements_valid and measurement_status (NPZ records validity).
Fast scene changes and delayed header min/max are deliberately accepted;
those are not reliable shutter/corruption detectors. Replay of the captured
freeze/recovery passes. No auto-shutter settings were changed; original
settings and the unresolved auto-shutter readback remain as documented above.

Host control of auto calibration (2026-10-05)
--------------------------------------------
Current protection was committed/pushed as 4f04f54 (379 tests passed).
Viewer closed; single USB owner used for the experiments below. Original
brightness, contrast, enhancement and thermometry blocks were recorded in
local diagnostics/auto-calibrate-audit/probe.json before any control writes.

Primary vendor documentation now located:
https://web-file.topdon.com/topdon-web/information_download/TopInfrared-User-Manual.pdf
Page 7 explicitly describes both a one-shot manual shutter calibration and
an Auto Shutter on/off switch. It notes that disabling automatic calibration
can compromise temperature accuracy. The manual predates the Duo and covers
several TOPDON products, so the local hardware observations remain necessary.
The TC002C Duo manual confirms that clicks are automatic shutter operation:
https://web-file.topdon.com/topdon-web/information_download/TC002C-Duo-User-Manual-EN.pdf

Recovered phone implementation (HikCmdUtil.java, lines 443..483):
- shutter(userId) calls USB_SetImageManualCorrect(userId).
- setAutoShutter(userId, enabled) uses USB_SetSystemSerialData with byMode=2,
  wDeviceCMDFlag=0, dwDeviceCMD=0x2001, dwValue=enabled ? 1 : 0.
- It then polls USB_GetCommandState, sleeping 50 ms while status is busy.
- Only auto enable/disable and the unrelated cover-calibration command occur
  in this serial-control call site. No calibration interval, temperature-change
  threshold, or 'calibration needed' getter has been established for this model.
- SDK Linux ConvertData<USB_SYSTEM_SERIAL_DATA_TRANSMISSION> at 0x200888 packs
  exactly 11 bytes: mode byte 0, flag uint16 at 1, command uint32 at 3, value uint32
  at 7. ParseRecvData at0x1fe102 unpacks the same fields. Native C struct padding
  and dwSize must NOT be included in the USB payload.

One-shot manual calibration, validated by frame flags:
  Select [2,4] via selector 5; GET_LEN selector 2 returns 1; SET_CUR selector 2
  with payload 01. All requests retain wIndex0x0A00.
  Payload 00 had no flagged event in two tests. Payload 01 triggered flagged
  events after two separate requests (12.037 -> 12.787 s; 34.027 -> 34.772 s).
  Another payload 01 event was observed with auto commanded off in each of two
  subsequent runs. The one-byte payload's channel/trigger interpretation is
  not independently defined here; payload 01 is the observed working value.
  Some manual control transfers delay the capture loop about 0.7 seconds,
  leaving only the final two flagged frames observable on this single-thread
  transport. Do not interpret those two frames as the entire mechanical cycle.
  Their raw planes were changing, unlike the repeated plane in the first
  automatic trace: the firmware flag must be honored even without identical
  pixels. No configuration-block changes resulted from manual triggering.

Auto switch wire payloads:
  Select [1,24] via selector 5; GET_LEN selector 1 returns 11; SET_CUR selector 1:
  off: 0200000120000000000000
  on:  0200000120000001000000
  GET command status directly from selector 6 (GET_LEN then GET_CUR), without
  changing the selector 5 command selection. 00=success, 01=busy; other codes
  are errors as documented above. Do not reselect [1,3] to poll command state.

Experimental caveat: the first off/on harness incorrectly polled [1,3], which
is not the status selector. Its status values must be discarded, and its
absence of automatic events is not sufficient evidence of suppression. The
corrected harness (schedule_probe_v2.py) uses selector 6; off, manual and on
commands returned status 00. Its trace and results are stored separately as
schedule-trace-v2.npz and schedule-probe-v2.json. After commanding on, a fresh
16-frame frozen-data event began about 0.75 seconds after the request. This
corroborates the switch's action on the actual camera, beyond transfer success.

Original auto readback remains unavailable: mode 1/flag 0/command0x2001 read
requests returned eleven zeros, with no command echo, after several delays.
These zeros must not be interpreted as an original 'off' value. The first
switch experiment waited for an uncommanded frozen-data event before sending
'off'; original enabled operation was inferred from that behavior, not read
from a valid getter. Every switch experiment sends on again in its finally
block. All four saved configuration blocks are compared before/after.

Integration design supported by this research:
- Offer 'Calibrate now' using the verified one-shot command, and an automatic
  calibration mode using the phone's auto-shutter command. Retain automatic
  operation as the default and re-enable it on exit/error after a manual window.
- Queue commands to the existing camera USB owner. Do not run calibration
  commands through a second camera connection or block the GUI with a transfer.
- For controlled experiments, calibrate before acquisition, temporarily disable
  firmware automation, and issue intentional calibrations at planned boundaries
  or a host-selected interval. Continue to flag the resulting unavailable data.
- Manual scheduling moves the gaps; it cannot supply temperature measurements
  while the shutter obstructs the scene. Preserve pause timestamps/reasons for
  later analysis instead of treating held readings as fresh measurements.
- No universal accurate interval has been established. Sensor warm-up and
  ambient changes can require calibration; scene temperatures alone cannot
  distinguish real changes from detector drift. A longer thermal-drift test
  with an independent stable reference is needed to quantify accuracy and
  validate extended suppression. Power-cycle persistence is also untested.

Corrected switch experiment result:
  baseline: 250 frames, approximately 10 seconds, no frozen frames.
  auto commanded off: approximately 60 seconds, with one requested manual
  calibration at 40.106 seconds; two final flagged frames followed at 40.853.
  No other flagged events occurred in that off window.
  auto commanded on: request completed at 70.147 seconds; 16 consecutive
  flagged frames at 70.901..71.498, live again at 71.538. Continued acquisition
  for approximately 75 seconds in restored mode, 3,608 total frames.
  The switch's behavior is corroborated within this bounded test; indefinite
  suppression under sensor/ambient temperature drift remains unverified.

Final read-only verification after all experiments:
  selector 6 status 00 after auto restore; all four original configuration blocks
  still byte-for-byte equal to the initial snapshot. A serial mode 1 read after
  correct selector 6 status polling also returned status 00 plus eleven zeros,
  so the getter still provides no usable auto-state readback. USB ownership
  was released and the viewer can reopen. Evidence: final-verification.json.

Camera-control integration (2026-10-05)
-------------------------------------
User decision supersedes the default proposed above: Auto calibrate defaults
to off in Camera settings, with a saved on/off preference applied on launch.
Calibrate now is available from the image context menu, including with no
spots. Logging and active reference measurements lock these controls. Commands
run through the existing camera owner, poll selector 6 with a bounded deadline,
and do not use the unavailable mailbox getter as verification. Exit re-enables
automatic operation, including after an uncertain failed auto-switch write;
the saved user preference remains unchanged. Numeric hardware restore and
display reset preserve the switch choice and saved calibration references.

-----------------------------------------------------------------

continue, but complete mode-8 frames stop arriving for tens of seconds or
minutes. The capture thread keeps the GUI responsive and rejects these frames;
it has not eliminated the underlying stream problem. Focus and resize tests
held 25 complete frames/s in each 15-second phase; this does not establish that
longer focus/resize interactions cannot contribute. No edits or tests were
running during subsequent failures.

timestamps, scene summaries/coordinates, and the candidate checksum. No
additional stream-fault flag has been identified. This comparison does not
prove that an undiscovered status field never changes during other failures.

Separate command status: related HCUSBSDK USB_COMMAND_STATE documents 0x0C
as USB_ERROR_BULK_DATA_EXCEPTION, plus 0x0A internal execution and 0x0B protocol
exceptions. These are control responses, not established telemetry fields.
Whether selector 6 reports unsolicited ongoing capture failures is unverified;
future probing must use the existing USB owner without concurrent claiming.

Public primary-source findings:
1. TOPDON's manual documents normal shutter clicks and reconnecting an
   unresponsive device; it does not describe this short-frame/corruption case.
   https://web-file.topdon.com/topdon-web/information_download/TC002C-Duo-User-Manual-EN.pdf
2. Another TC002C Duo Linux implementation reports desynchronized/tiled frames,
   rejects them, and reopens its stream after consecutive unusable frames.
   Its OpenCV/V4L2 acquisition path differs from our direct USB path. Its
   reported fixes are useful leads, not a validated diagnosis for this viewer.
   https://github.com/leswright1977/PyThermalCamera/pull/29
3. Teledyne's USB 3.1 camera engineering note describes camera-buffer overflow
   partially overwriting images when host requests fall behind. Our camera
   uses USB 2.0, so this is a related mechanism, not model-specific proof.
   https://www.teledynevisionsolutions.com/support/support-center/whitepaper/iis/enhancing-usb-3.1-cameras-reliability-with-frame-buffer/
4. libuvc queues asynchronous bulk transfers and explicitly documents using
   many buffers to avoid missed transfers from scheduling delays. Its current
   default is 100 buffers on non-Apple platforms, 20 on Apple. Our dedicated
   capture thread still submits one synchronous USB read at a time.
   https://github.com/libuvc/libuvc/blob/master/src/stream.c
   https://github.com/libuvc/libuvc/blob/master/include/libuvc/libuvc_internal.h
5. libusb documents short successful transfers and partial data on timeout.
   PyUSB accepts partial-timeout data internally. The measured reads during
   this failure were roughly 20-30 ms, versus the configured 2 s timeout,
   so hidden partial timeouts do not explain these particular captures.
   https://libusb.sourceforge.io/api-1.0/group__libusb__syncio.html

Queued capture validation (2026-10-05 local / 2026-10-06 UTC):
The Linux desktop kept 32 asynchronous bulk reads submitted on the existing
libusb connection. The first trial ran 21.5 minutes with 32,230 valid frames,
no additional size rejections after startup, and no USB timeouts. Clean shutdown
cancelled the pending transfers and released the viewer, watcher, and awake
helper. A repeat passed 42 minutes with 63,481 valid frames at approximately
25 fps, no new rejections after startup, and no USB timeouts; the UI heartbeat
remained healthy. The user reported sustained stability and accepted the fix.
This supports queued acquisition as the practical fix; it does not establish
the camera firmware's precise failure mechanism. The Linux desktop now defaults
to depth 32, with --usb-queue-depth 0 retaining the synchronous fallback. macOS
and the generic camera API retain their synchronous defaults pending validation.
