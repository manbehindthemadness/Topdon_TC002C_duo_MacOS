Anime4K enhancement: source and model acquisition
================================================

The official Android app's regular TC002C Duo TISR path selects Anime4K09,
not ACNet. Anime4K09 is a rule-based upscaler with no trained weights.
This follows the Java creator's GPU selection and the ARM64 native constructor
call to Anime4KCPP::OpenCL::Anime4K09 (see hardware-research.txt).
The iOS app has not been inspected.

Normal Android Anime4K09 parameters
----------------------------------
passes=3, pushColorCount=1, strengthColor=0.0, strengthGradient=0.5,
zoomFactor=2.0, fastMode=false, videoMode=false, preprocessing=false,
postprocessing=false, preFilters=4, postFilters=48, alpha=true.
SupHelp also supplies HDN=true and HDNLevel=2 in its parameter object, but the
non-CNN An4KGPU constructor does not pass those fields to the native algorithm.

ACNet models obtained and verified separately
--------------------------------------------
Each of the four public legacy variants contains 4,784 float parameters:
4,712 kernels and 72 biases. Read-only comparisons with the official APK's
exported CPU constants, after accounting for layer storage order, match every
array within 1e-7 (largest absolute difference 5.960464477539063e-08).
Some arrays are byte-identical; others differ by decimal/float rounding.
This supports a matching parameter set, not identical end-to-end phone output.

Runnable local test
------------------
Built the modern CPU-only CLI with:
  cmake -S /usr/src/Anime4KCPP-modern -B /usr/src/Anime4KCPP-modern/build \
    -DAC_BUILD_CLI=ON -DAC_BUILD_VIDEO=OFF -DAC_BUILD_GUI=OFF \
    -DAC_CORE_WITH_OPENCL=OFF -DAC_CORE_WITH_CUDA=OFF -DAC_ENABLE_LTO=OFF
  cmake --build /usr/src/Anime4KCPP-modern/build -j4

Run from this repository:
  /usr/src/Anime4KCPP-modern/build/bin/ac_cli \
    -i diagnostics/telemetry-research/anime-models/fan-native-input.png \
    -o diagnostics/telemetry-research/anime-models/fan-native-acnet-hdn2.png \
    -m acnet-legacy-hdn2 -p cpu -f 2

This succeeded at 256x192 -> 512x384, using CPU FMA. One inference took
39.247 ms; that single run is not a sustained frame-rate benchmark.
The input was downsampled from a saved, already rendered fan preview, so this
does not demonstrate recovered sensor detail or reproduce the phone pipeline.
Viewer integration
------------------
Camera -> Upsampling algorithm offers Anime4K09 and all four legacy HDN variants,
default Off. Bundled ONNX models use the existing OpenCV CPU backend on both platforms,
so the viewer does not require an Anime4KCPP native build, a model download, or
the ONNX Python package. The ONNX package is only needed to regenerate models.
The MIT license and provenance ship beside the four models in topdon_duo/models.

tools/export_acnet.py converts pinned public source parameters into nine
Conv3x3/ReLU stages with replicated edge padding and a stride-2 ConvTranspose2x2.
Independent upstream CPU golden images check all four variants, including borders
and output ordering. The initial HDN2 comparison was pixel-identical; regression
tests allow one uint8 level across CPU architectures and OpenCV builds.

The network processes the filtered intensity plane before display
colorization, or luminance with resized chroma for a hardware color preview.
Enhancement input size defaults to native sensor dimensions (256x192), with a
Full preview option that preserves the complete 512x384 camera preview. Native
mode matches the Android callback's input/output sizes; downsampling an enlarged
preview is not proof of identical native samples from the phone's stream.
Final display geometry and measurement grids stay unchanged, so spots and saved
raw counts are independent of model output. Saved rendered images and recordings
include enhancement. Saved still-image JSON metadata records the selected
upsampling setting.

Anime4K09 implementation
-----------------------
anime4k09.py ports the public v2.5.0 OpenCL getGray/getGradient/pushGradient rules
to NumPy/OpenCV, using 2x linear resize, 3 passes, gradient strength 0.5, color
strength 0, clamp-to-edge sampling and UNORM8 intermediate quantization.
Processing occurs after palette conversion, as on the inspected Android path.
The original MIT license is included as models/LICENSE-ANIME4K09.txt.
An independent scalar C++ harness of the original public OpenCL kernels checks
edge passes within one uint8 level. The port is not claimed bit-identical to
phone GPU arithmetic, nor has the iOS implementation been identified.

Enhancement amount (0..1, default 1) scales Anime4K09 gradient strength or blends
ACNet output with cubic interpolation. Zero bypasses processing and retains the
original image. Anime4K09 passes (1..5, default 3) affect only Anime4K09.
These are synchronous CPU paths; the phone's GPU performance does not carry
over to the portable implementation. Fewer passes and native input reduce cost.

Models are loaded lazily and reused. Failed loading/inference falls back to the
unenhanced image and reports a Camera status error; selecting Off clears it.
The synchronous CPU path avoids displaying a previous frame's enhanced image
alongside current measurements. Full preview processing can reduce frame rate.
On the local Linux machine, short OpenCV CPU inference runs took approximately
22-34 ms at 256x192 and 78-85 ms at 512x384. These are not macOS benchmarks.
